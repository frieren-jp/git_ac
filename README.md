# Лабораторная работа №2

Тема: настройка CI в GitHub Actions для Node.js.

Репозиторий: https://github.com/frieren-jp/git_ac

Учебный проект складывает два числа и проверяет аргументы. Пайплайн устанавливает зависимости, запускает ESLint и модульные тесты.

## Запуск

Из корня проекта:

```sh
cd src
npm ci
npm start
npm run lint
npm test
```

В Linux из корня также доступны команды `make lint`, `make test`, `make start`.

## Конфигурация CI

Файл: `.github/workflows/ci.yml`. Триггеры: push в main/master, pull request с целевой веткой main/master и ручной запуск. Ubuntu 22.04, лимит 15 минут. Node.js 18.x и actions v4 оставлены в соответствии с методичкой. Рабочая директория npm — src; Makefile расположен в корне.

## Проверка отказоустойчивости

В отдельном учебном коммите в src/calculator.js удаляется закрывающая скобка в объявлении функции. ESLint должен завершиться с Parsing error; следующий коммит восстанавливает скобку. Итоговая версия должна проходить проверки.

## Ответы на контрольные вопросы

1. **Какую проблему решает CI?** Автоматически проверяет каждое изменение, помогает рано обнаружить ошибки интеграции и обеспечивает одинаковые проверки для всех участников команды.
2. **За что отвечают on и branches?** on задаёт события запуска. branches фильтрует ветки: для push — ветку коммита, для pull_request — целевую ветку запроса.
3. **Почему npm ci?** Команда устанавливает зависимости по package-lock.json, удаляет существующий node_modules и не обновляет lock-файл. При несогласованности package.json и lock-файла она завершается ошибкой. Это делает установку воспроизводимой. npm install может изменять lock-файл.
4. **Как линтер защищает main/master?** ESLint обнаруживает синтаксические ошибки, неопределённые и неиспользуемые переменные; ненулевой код выхода делает CI неуспешным. Чтобы GitHub запрещал слияние при ошибке, проверку validate-and-test нужно назначить обязательной в правилах защиты ветки. Сам workflow не блокирует прямой push и не выявляет все логические ошибки; для последних добавлены тесты.
